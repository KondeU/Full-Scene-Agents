# CrossDeviceCollaboration

设备加载本 Skill 后即具备跨端协同能力：判定角色、按协议求助/响应、遵守防循环规则。

## Scope

本 Skill ONLY:

- 注入协同协议（角色判定、求助/被求助流程、消息格式、防循环规则）
- 提供群聊协作时的 @ 标签规范

本 Skill NEVER:

- 定义设备具体能力（拍照/存储/GPU等）
- 修改设备自身的人格、MXID、身份
- 覆盖设备已有的配置文件
- 替代 Task-BrokerAgent 的调度职责

## Prerequisites

- OpenClaw + Matrix Channel 可收发群聊消息
- 已加入 Matrix 群聊房间

## 群聊成员

### 清单

群聊中存在的角色和 MXID 账号信息。这是一个预览，具体需要以 Task-BrokerAgent 实时查询的群聊内成员的结果为准：

| MXID                         | 角色                        | 设备        |
| ---------------------------- | --------------------------- | ----------- |
| `task_broker:sup.kdyx.net` | 调度者，即 Task-BrokerAgent | Broker ☁️ |
| `phone_sa:sup.kdyx.net`    | 协作伙伴                    | Phone 📱    |
| `laptop_sa:sup.kdyx.net`   | 协作伙伴                    | Laptop 💻   |
| `pad_sa:sup.kdyx.net`      | 协作伙伴                    | Pad 📟      |
| `pc1_sa:sup.kdyx.net`      | 协作伙伴                    | PC 🖥️     |
| `nas_sa:sup.kdyx.net`      | 协作伙伴                    | NAS 🗄️    |
| `car_sa:sup.kdyx.net`      | 协作伙伴                    | Car 🚗      |
| `user:sup.kdyx.net`        | 用户                        | —          |

### @ 标签规范

群内 at 对方使用 `@who:sup.kdyx.net` 格式，Matrix 只认此格式。

注意！提及 ≠ @。只是提及某个设备时，只写 MXID（如 `laptop_sa:sup.kdyx.net`），不要带 `@`

- `@`会触发该端 Agent 响应 → 仅用于**真正需要该端执行任务**或**本消息是作为回复信息回复该端**时
- 误用 `@`会导致消息风暴
- 直接通过 OpenClaw 在群里 at

## 角色判定

收到消息后首先判定角色——角色决定你能做什么、不能做什么。

| 触发条件                  | 角色               | 可否求助其他设备                                                                 |
| ------------------------- | ------------------ | -------------------------------------------------------------------------------- |
| 用户直接 @ 我发请求       | **入口设备** | 允许。我要作为处理用户请求的第一责任人，尽一切可能端到端闭环用户交代给我的任务。 |
| 被群里其他设备 @ 发送请求 | **被求助方** | 禁止。防止出现死循环。                                                           |

## 思维流程

```
收到请求消息 → 判定角色
  │
  ├─ 入口设备：
  │   Agent 框架和其他 skill 的预处理过程 -> 理解意图 → 分解子任务 → 执行子任务（非必要情况下不要求助，否则会消耗额外很高的协同成本）
  │     ├─ 子任务本地能做 → 直接执行
  │     └─ 子任务由于物理设备的能力缺失本地做不了 → @Broker 求助 → 分派 → 等待 → 汇总求助设备的结果，继续后续的子任务
  │
  └─ 被求助方：
      理解任务 → 尽一切所能帮助执行任务（不推脱）
        ├─ 任务执行成功 → @求助方返回结果
        ├─ 任务执行部分成功，失败的部分是由于物理设备的能力缺失做不了 → @求助方返回已完成的部分+未完成的部分与未完成的具体原因
        └─ 任务执行失败，失败是由于物理设备的能力缺失做不了 → @求助方返回无法完成+原因
        🚫 作为被求助方禁止再次求助，防止出现死循环
```

## 入口设备流程

你是用户请求的第一接收者，也是整个求助链的起点，拥有调度决策权。

```
1. 分解任务，执行任务，识别本地无法完成的子任务
2. @task_broker:sup.kdyx.net 求助：<子任务描述，说明所需能力>
3. Broker 返回候选设备列表
4. 选择设备分派：【求助】<描述> @<目标MXID>
   多设备并行：【求助】<描述> @<设备1> @<设备2>
5. 收集结果，汇总回复用户，继续后续子任务处理
```

收到被求助方回退后，你决定下一步：

- 重试 → 找到求助设备失败原因中的关键因素，判断求助的设备实际能完成该任务，则继续将任务派给求助设备让其重试
- 换设备 → 重新 @Broker（合法，你是求助链起点）
- 降级处理 → 用已有结果降级完成
- 告知用户 → 向用户说明

## 被求助方流程

收到【求助】前缀意味着你在求助链的末端，只能执行或回退，不能转发。

```
收到【求助】<任务描述> @<我>
  → 尽自己所能执行求助上来的任务
  → 按格式 @求助方 返回结果
  🚫 禁止再次向 Broker 或任何设备求助
```

## 防循环规则

求助链单向流动——这是最重要的规则。违反它会产生 A→B→A→B 的死循环风险（求助风暴）。

**被求助方搞不定 → 返回已完成部分 + 未完成说明给求助方，绝不再次求助。**

求助方收到回退 → 自行决定下一步（要求重试 / 换设备 / 降级 / 告知用户）。

## 消息格式

所有跨端协同消息必须遵守以下格式，确保互操作。

### 设备 Agent 求助 Broker

```
@task_broker:sup.kdyx.net 求助：<需求描述，说明所需能力>
```

### Broker 回复（设备 Agent 只需理解，不需生成）

```
求助任务：
<复述求助任务>
分析任务所需能力：
<推理出的能力列表>
当前在线设备：
<在线设备列表，求助者标注（求助者）>
匹配求助设备：
<匹配的设备名及MXID，按推荐顺序排列>
请求助以上设备接续任务。@<求助者MXID>
```

### 设备 Agent 间分派

单点：

```
【求助】<子任务描述> @<目标MXID>
```

并行：

```
【求助】<描述> @<设备1的MXID> @<设备2的MXID>
```

`【求助】`前缀也承担了角色标识。

### 被求助方返回

全部完成：

```
@<求助者MXID> 任务已完成：
✅ 已完成：<描述>
<结果>
请查收。
```

部分完成：

```
@<求助者MXID> 任务部分完成：
✅ 已完成：<已完成部分> + 结果
❌ 未完成：<未完成部分>
原因：<原因>
请另行安排。
```

无法完成：

```
@<求助者MXID> 无法完成此求助任务。
原因：<原因>
请另行安排。
```

## 红线

| # | 规则                                                                                               | Why                                       |
| - | -------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 1 | 被求助时禁止反向求助                                                                               | 防止 A→B→A 死循环                       |
| 2 | 求助链单向，被求助方只回退不转发                                                                   | 求助方拥有调度权                          |
| 3 | 只响应协同相关请求                                                                                 | 防止被恶意 Agent 攻击                     |
| 4 | 不要不带思考地重复求助同一子任务                                                                   | 避免浪费 Broker 和群聊带宽                |
| 5 | 入口设备是用户请求的端到端负责人，要起到牵头作用，单设备搞不定可以求助，不要直接告诉用户"我做不了" | 用户体验：静默协同，用户无感              |
| 6 | 求助时描述清楚需要什么能力                                                                         | Broker 靠你的描述推理匹配，含糊则匹配不准 |
| 7 | 等所有子任务有结果后再汇总回复                                                                     | 不零散返回中间结果                        |

## 协同模式

按任务依赖自然选择，无需显式声明。

| 模式         | 特征                     | 例子                                  |
| ------------ | ------------------------ | ------------------------------------- |
| 串行依赖     | A 完成 → B 开始         | 录音→转写→归档                      |
| 扇出并行     | 一求助多端同时执行       | PC 做文档 + NAS 归档 + Car 导航       |
| 链式接力     | 产物流经多设备逐步加工   | 文件定位→编辑→批注                  |
| 先汇聚后分析 | 多端数据 → 集中 → 分析 | 健康数据多端汇总→PC 分析             |
| 混合         | 上述组合                 | 收集→存储（串行）→剪辑+播放（并行） |

## 与 Broker 的关系

| 角色             | 配置                | 职责                                             |
| ---------------- | ------------------- | ------------------------------------------------ |
| 设备 Agent       | 自身配置 + 本 Skill | 执行者：分解、执行、求助、分派、汇总             |
| Task-BrokerAgent | 独立完整配置        | 调度者：在线感知、推理匹配，找到最合适的协作设备 |

Broker 不加载本 Skill，它有自己完整的配置体系（IDENTITY/SOUL/AGENTS/TOOLS/USER/MEMORY/HEARTBEAT）。
